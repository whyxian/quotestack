# quotestack 代码审查报告

> 审查日期：2026-11-10
> 审查范围：`src/quotestack/` 全部 53 个 Python 文件（7,660 行）+ 测试 + 关键文档
> 基线：`e8c33d0` 及当时工作区中的文档改动
> 方法：逐层静态阅读、`ruff` / `mypy` / `pytest --cov`、用 fake source 做最小复现；未跑真实行情探测与压测
> 限制：不覆盖上游接口的线上稳定性；行情是否“当前正确”不在本次范围内，本次只看代码是否按契约工作

---

## 0. 结论

**架构没有需要推翻的问题，但核心数据路径有 2 个 P0、6 个 P1。**

做得好的部分很明显：分层干净、错误统一在 `sources/transport.py` 收口、缓存三态和单飞是独立机制、金额一律 `str`、`ruff` 和 `mypy` 全过、测试 298 个且行覆盖率 91.34%。

问题集中在三个地方：

1. **缓存键/分页这类“边界算术”**：错了不会抛异常，只会返回错的数据。
2. **批量与降级路径**：单条失败会拖垮整批，非重试错误会冷却整个源。
3. **契约与实现漂移**：文档承诺的 crypto、`status`、`CLIENT_BROKEN`、`source` 字段，代码里没有对应行为。

### 发现统计

| 级别 | 数量 | 含义 |
|---|---:|---|
| P0 | 2 | 会返回错数据，或核心接口不可用 |
| P1 | 6 | 高风险：功能不可用、资源无界、契约被破坏 |
| P2 | 12 | 中风险：局部错误、性能、可观测性、安全 |
| P3 | 4 | 低风险：死代码、格式、文档漂移 |

### 最该先修的 5 个

1. `history()` 的缓存键漏了 `limit`，一次小查询会把后续大查询钉死（CR-01）。
2. `/v1/instruments` 的 `has_more` 永远为 `false`，客户端无法翻页（CR-02）。
3. crypto 标的声称有 `QUOTE` / `HISTORY`，但没有任何路由，调用必然 `UNAVAILABLE`（CR-03）。
4. `quote_many()` 的“单条失败不影响整批”在源端缺数据时不成立，合法标的也会一起失败（CR-04）。
5. 限流只覆盖部分路径，`fx` / `iter_instruments` / 估值内部调用可以绕过令牌桶（CR-07）。

## 3. P0：会返回错数据或核心接口不可用

### CR-01 `history` 缓存键不含 `limit`

**位置**

- `src/quotestack/client/__init__.py:347-362`：键由 `capability + instrument + interval + adjust` 组成。
- `src/quotestack/client/__init__.py:1010-1020`：`_fetch_history` 把 `limit` 传给源，源按 `limit` 返回。
- `src/quotestack/cache/base.py:35`：`HISTORY` 默认 TTL 1 小时。

**复现**

用一个返回固定条数的 fake source：

```text
history(limit=5)  -> 5
history(limit=50) -> 5    # 期望 50
```

`history(limit=5)` 先把 5 根写入缓存；后续 `limit=50` 命中同一个键，直接切片 `[-50:]`，结果仍是 5 根。单飞也会让并发的不同 `limit` 共用同一个任务。

**影响**

同一进程内最多 1 小时（默认 TTL）返回错误根数；server 的 `/v1/history` 对客户端表现为“limit 不生效”。如果按 `len(bars)` 做指标或画图，会静默缺数据。

**建议**

- 把 `limit` 放进缓存键；或缓存一个规范上限（如 5000）再在客户端切片。
- 若选前者，注意键会按 `limit` 分片；若选后者，首次小请求成本会变大。
- 单飞键必须与最终缓存键一致。

**测试**

新增回归：`limit=5` 后再 `limit=50` 必须返回 50 根；并发两个不同 `limit` 也必须各自正确。

### CR-02 `/v1/instruments` 的 `has_more` 永远为 `false`

**位置**

- `src/quotestack/server/app.py:446-471`。

**问题**

代码先收集到 `target = page * page_size` 条，然后：

```text
items=items[:page_size]
has_more=len(items) > page_size
```

`items` 已经被切到 `page_size`，所以 `len(items) > page_size` 几乎永远为假。只有一批数据越过 `page_size` 时才可能为真。

**复现**

用 fake client 两条数据、`page_size=1`：

```text
GET /v1/instruments?asset_class=STOCK&market=CN&page_size=1
data.has_more = false
data.next_page = null
```

实际还有第二条数据，但客户端会认为已经结束。

**影响**

依赖 `has_more` / `next_page` 的调用方只能拿到第一页；分页接口形同虚设。深页还有 O(N²) 重新扫描的问题：第 N 页会从头遍历 `N * page_size` 条。

**建议**

- 在切片前判断：多取一条（`page_size + 1`），用第 `page_size + 1` 条是否存在决定 `has_more`。
- 更好的做法是给 `iter_instruments` 增加游标/快照能力，避免深页重扫。
- 给 `page` 设上限，避免无意义的深页扫描。

**测试**

`has_more=true` 的用例必须存在；当前 `test_listing_is_paginated` 只断言了第一页条数和 `page`，没有断言 `has_more`。

## 4. P1：高风险

### CR-03 crypto 声明了 QUOTE/HISTORY，但没有路由

**位置**

- `src/quotestack/identity/resolver.py:147-165`：crypto 使用 `_CAPABILITIES_LISTED`，得到 `QUOTE` 和 `HISTORY`。
- `src/quotestack/sources/routing.py:21-39`：没有 `(CRYPTO, CRYPTO, QUOTE/HISTORY)`。
- `src/quotestack/sources/binance.py:31-37`：Binance 只声明 `LIST`。
- `tests/test_routing.py:56`：测试明确断言 crypto 没有 quote 路由。
- `guide/02-concepts.md:50`：指南写 `CN:CRYPTO:BTCUSDT` 支持“报价、K 线”。

**复现**

```text
resolve("BTC", CRYPTO, CRYPTO)
  -> CRYPTO:CRYPTO:BTC  capabilities={HISTORY, QUOTE}  alias={'binance': 'BTCUSDT'}

quote("BTC", CRYPTO, CRYPTO)
  -> UnavailableError: all sources failed
```

源没有路由，`_fetch_and_store` 的候选列表为空，直接走“所有源失败”。

**额外问题**

`resolve("BTCUSDT", CRYPTO, CRYPTO)` 会生成别名 `BTCUSDTUSDT`，把交易对当成 base asset 再拼一次。

**影响**

文档承诺的 crypto 报价/K 线不可用；错误还是 `UNAVAILABLE`，不是 `UNSUPPORTED`，调用方会误以为“临时故障”，从而重试。

**建议**

- 二选一：实现 Binance 的 quote/history 与路由；或把 crypto 能力改成只有 `LIST`，文档同步收紧。
- 输入规范化：如果用户传的是 `BTCUSDT`，不要再次追加 `USDT`。
- 把 `tests/test_routing.py:56` 的预期与产品能力对齐，不要用测试固化“文档说支持、代码不支持”。

### CR-04 `quote_many` 的单条隔离不成立；非重试错误会冷却源

**位置**

- `src/quotestack/client/__init__.py:985-1008`：`_fetch_group` 以整批调用 `source.quote(instruments)`。
- `src/quotestack/sources/eastmoney/quotes.py:76-105`：只要有一个代码缺行，整个批次抛 `EmptyResponseError`。
- `src/quotestack/sources/tencent.py:96-115`：同样的整批缺失处理。

**复现**

fake source 对整批抛 `EmptyResponseError`，请求 `[600519, 000001]`：

```text
600519 False  UNAVAILABLE: no source served CN:STOCK:600519
000001 False  UNAVAILABLE: no source served CN:STOCK:000001
cooldown after one batch: False
cooldown after two batches: True
```

合法的 600519 也失败；连续两批后，源被冷却 30 秒。

**影响**

- 违反 `/v1/quotes/batch` 和指南里“单条失败不影响其余”的承诺。
- `EmptyResponseError.retryable=False`，但 `_fetch_group` 无条件 `mark_failed`，把“某只票没数据”升级成“整个源不可用”。
- 批量路径还绕过了 `FetchPolicy` 的单飞和 stale 回退；`fresh_entry` 只接受新鲜缓存，批量调用不会像单条 `quote` 那样退到 stale。

**建议**

- 给源增加“部分结果 + missing”的返回契约，或对 missing 的条目单独重试，而不是整批失败。
- 只对 `exc.retryable` 的错误 `mark_failed`，与 `FetchPolicy` 保持一致。
- 批量路径复用 `FetchPolicy` 的缓存/降级语义，或明确文档化差异。
- `zip(..., strict=True)` 在源返回长度不一致时会抛 `ValueError`；应转成 `SchemaChangedError`。

**测试**

构造“一个有效 + 一个源端缺失”的批次；断言有效条目仍成功，源不被冷却。

### CR-05 `limit` / `page_size` 没有在库层校验

**位置**

- `src/quotestack/client/__init__.py:324-362`：`history`。
- `src/quotestack/client/__init__.py:804-835`：`nav`。
- `src/quotestack/client/__init__.py:864-930`：`iter_instruments`。

**复现**

fake source 固定返回 10 条：

```text
history(limit=0)  -> 10 条（期望报错）
history(limit=-3) -> 7 条（丢掉前 3 条，期望报错）
```

`iter_instruments(page_size=0)` 在 Tiantian/Binance 上会直接 `ValueError: range() arg 3 must not be zero`；Eastmoney 则静默改成 1。行为不一致。

**影响**

server 层有 `ge=1`，但库的公开 API 没有；脚本、CLI、同步封装都可能传入非法值，得到静默错误或裸 `ValueError`。

**建议**

在公开入口统一校验：`limit >= 1`、`page_size >= 1`、`max_age` 非负；抛 `InvalidArgumentError`。与 `holdings()` 的现有校验保持一致。

**测试**

参数化覆盖 `0`、负数、非整数；断言 `InvalidArgumentError`，而不是“返回全部/丢前几条”。

### CR-06 `estimate()` 在索引/持仓/报价失败时会抛异常

**位置**

- `src/quotestack/client/__init__.py:396-404`：`try` 只包住 `profile()` 和 `_allocation()`。
- `src/quotestack/client/__init__.py:451`、`460`：索引解析、指数报价在 `try` 之外。
- `src/quotestack/client/__init__.py:488`、`513`、`521`、`527`：持仓、个股报价、基准解析也都在 `try` 之外。
- `guide/05-estimate.md:131`：“都不会抛异常”。

**复现**

fake fund + fake market，让 `quotes_by_secid` 抛 `UpstreamError`：

```text
estimate raised: UpstreamError UPSTREAM_ERROR
```

**影响**

指数型基金在指数搜索/报价失败、主动基金在持仓/报价失败时，调用方拿到异常，而不是 `change_pct=None`；与“尽力而为”的契约相反。

**建议**

把整个推导过程包进降级逻辑，或给每一步定义“可降级”的错误集合（`UpstreamError` 系列）；`UnsupportedError` 仍可抛。区分“输入缺失”和“实现 bug”。

**测试**

分别让 `resolve_index`、`quotes_by_secid`、`holdings` 抛 `UpstreamError`，断言返回 `Estimate(basis=NONE, change_pct=None)` 且 `explanation` 有原因。

### CR-07 限流只覆盖部分路径

**位置**

`FetchPolicy` 和 `_fetch_group` 会用 `self._bucket.acquire()`，但以下路径直接调用源：

- `src/quotestack/client/__init__.py:560-565`：`_quotes_by_secid`。
- `src/quotestack/client/__init__.py:666-675`：`_resolve_index`。
- `src/quotestack/client/__init__.py:684-690`：`_index_history`。
- `src/quotestack/client/__init__.py:819-828`：`fx`。
- `src/quotestack/client/__init__.py:914-930`：`iter_instruments`。
- `src/quotestack/client/__init__.py:451-527`：估值内部的指数/持仓/报价。

**影响**

- `estimate()` / `benchmark()` 一次调用可能发出多次上游请求，但都不进令牌桶。
- `iter_instruments()` 翻 60 页也不进桶；指南说“库内部限流 4 次/秒”，同页又说 A 股全量约 2.6 秒，两者不可能同时成立。
- `fx()` 没有缓存也没有限流，连续调用会直接打上游。

**建议**

把限流/冷却放到 **source 边界**（装饰器或一个统一的 `SourceGateway`），而不是只放在 `FetchPolicy`。至少让 `iter_instruments`、`fx`、`_quotes_by_secid`、`_resolve_index` 经过同一个 gate。否则“限流是库的保证”不成立。

**测试**

用 fake source 统计调用次数与时间，断言全量 listing 的请求间隔符合配置。

### CR-08 `MemoryCache` 无淘汰

**位置**

- `src/quotestack/cache/memory.py:12-17`：注释明确写“no eviction”。
- `src/quotestack/client/__init__.py`：`MarketData` 默认 `MemoryCache`；server 也一样。
- `src/quotestack/server/config.py:38`：`cache_dir` 存在，但没有任何持久化实现。

**影响**

长跑 server 会为每个 `(capability, instrument, interval, adjust, limit)` 永久保留条目；`HISTORY` 的 TTL 只有 1 小时，但过期条目不会删除。品种多、周期多时内存持续增长；`cache_dir` 又让人以为有持久化。

**建议**

- 增加容量上限 + LRU，或定期清扫 `age > max_stale` 的条目。
- 如果要做持久化，先实现 `cache_dir` 语义；否则删掉这个配置项，避免误导。
- 在 `/healthz` 暴露容量/命中率，而不仅是 `entries`。

**测试**

写入超过容量上限的键，断言旧条目被淘汰；长跑模拟下内存/条目数有界。

## 5. P2：中风险

### CR-09 `Quote.status` 从未被赋值

`src/quotestack/models/quote.py:39` 默认 `REALTIME`；`eastmoney/quotes.py`、`tencent.py` 构造 `Quote` 时都没有传 `status`；全仓只有读取，没有写入。`guide/03-quotes.md:22` 和 `guide/11-troubleshooting.md:21` 描述 `HISTORICAL` / `UNAVAILABLE`，当前永远看不到。

**建议**：要么在收盘/历史/降级时设置 `status`，要么删掉这两个枚举值和文档承诺。`is_usable` 目前恒为真，也是同一个问题的延伸。

### CR-10 `CLIENT_BROKEN` 不可达

`FetchPolicy` 对每个源捕获 `SchemaChangedError` 并继续；全部失败后统一抛 `UnavailableError`（`src/quotestack/client/fetch.py:170-181`、`202-246`）。`ClientBrokenError` 定义了、映射了 503，但没有任何 raise。设计文档和指南都承诺“所有源结构都变了 → CLIENT_BROKEN”。`DelistedError` 同样没有产生路径。

**建议**：在所有 attempt 的 `reason` 都是 `SCHEMA_CHANGED` 时抛 `ClientBrokenError`；否则保持 `UnavailableError`。为 `DELISTED` 增加明确来源，或从错误清单中删掉。

### CR-11 `/v1/history` / `/v1/nav` 的 `source` 是硬编码

`src/quotestack/server/app.py:259`：

```text
"source": bars[0].source if hasattr(bars[0], "source") else "eastmoney"
```

`Bar` 是 `slots=True` 的 dataclass，没有 `source` 字段，`hasattr` 永远为假，所以永远返回 `eastmoney`；`src/quotestack/server/app.py:286` 的 `nav` 直接写死 `tiantian`。自定义源或未来换源时，契约字段就是错的。`bars` 为空时 `bars[0]` 还会 `IndexError`。

**建议**：让 fetch/cache 返回实际 source，或给 `Bar` / `NavPoint` 增加 source；至少在响应层不要伪造。

### CR-12 CLI/HTTP health 泄露代理 userinfo

`src/quotestack/client/__init__.py:957-959` 把 `QUOTESTACK_PROXY_URL` / `HTTPS_PROXY` 原样放进 health；`src/quotestack/cli.py:215` 直接打印。代理 URL 常见形式是 `http://user:pass@host:port`，会进入终端、CI 日志或 `--json` 输出。server 的 `/v1/healthz` 反而过滤掉了 proxy，说明这个字段本来就不该外露。

**建议**：只返回 scheme/host（去掉 userinfo），或干脆不返回；CLI 输出同样脱敏。

### CR-13 时间戳解析失败回退到 `now()`

- `src/quotestack/sources/eastmoney/parsing.py:34-38`：非法/缺失的 `f124` → `datetime.now(_CN_TZ)`。
- `src/quotestack/sources/tencent.py:195-215`：解析失败 → `datetime.now(...)`。

这会把“源没给时间”变成“刚刚观测”，配合 CR-09 的 `status=REALTIME`，旧数据看起来是新的。

**建议**：抛 `SchemaChangedError`，或把 `ts` 设为 `None` 并引入“未知时间”状态；至少不要伪造当前时间。补一条坏时间戳 fixture。

### CR-14 指数解析 / FX / 基准历史没有缓存

`_resolve_index`（`client/__init__.py:666-675`）每次估值/基准都调 Eastmoney 搜索；`fx`（`:819-828`）每次全量拉取；`benchmark` 的 `_index_history`（`:684-690`）直接调源。`Capability.RESOLVE` 在缓存表里有 7 天 TTL，却没有被使用。

**建议**：把指数名→secid、FX 报价纳入现有缓存/限流；至少给 `resolve_index` 做进程内 LRU。

### CR-15 关闭时 in-flight 任务未等待

`src/quotestack/client/fetch.py:64-68` 只 `task.cancel()` 并清空字典；`src/quotestack/client/__init__.py:184-190` 紧接着 `await source.aclose()`。取消是异步投递的，源客户端可能在任务还没退出时被关闭。任务异常也没有 `task.exception()` 消费，可能产生“exception was never retrieved”。

**建议**：`await asyncio.gather(*tasks, return_exceptions=True)` 后再关闭源；done callback 里消费异常。

### CR-16 `SyncMarketData` 生命周期

`src/quotestack/sync.py:66-74` 先启动线程再构造 `MarketData`，构造失败会留下一个永远运行的 daemon loop；`_call`（`:80-82`）`future.result()` 没有超时，`close()`（`:97-111`）在 `aclose` 挂起时会一直阻塞；`_run_loop` 没有异常监控。

**建议**：先构造 client 再启动线程；`_call` 加超时；记录 loop 异常；`close` 失败也要保证线程停止。

### CR-17 `/v1/holdings` 的 `has_more` 恰好等于 limit

`src/quotestack/server/app.py:325`：`has_more = len(quarters) == limit`。当恰好取到最后一页时也为真，客户端会多请求一次空页。建议取 `limit + 1` 判断，或让 `holdings` 返回显式的 `has_more`。

### CR-18 `Retry-After` 没有落地

`docs/design/13-runtime-model.md:100` 要求尊重 `Retry-After`；`transport.check_status`（`src/quotestack/sources/transport.py:77-83`）只抛 `RateLimitedError`，没有解析 header；`RateLimitedError`（`src/quotestack/errors.py:146-149`）也没有 `retry_after` 字段。指南里的“等 retry_after”无处可取。

**建议**：解析 `Retry-After`（秒/HTTP date），放进错误 context，并让 `Cooldown` 使用它；否则删掉设计和指南里的承诺。

### CR-19 标识解析的边界

- `src/quotestack/identity/resolver.py:124-131`：`isalpha()` 拒绝 `BRK.B`、`BF.B` 等含点号的合法美股代码。
- `:163`：crypto 无条件拼 `USDT`，`BTCUSDT` → `BTCUSDTUSDT`。
- `:64-105`：`166002` 前缀是 `16`，被判为 listed，获得 `QUOTE`/`HISTORY`；`tests/test_identity.py:60-67` 把这个行为固化了。它实际是场外基金，`quote` 会走无意义的源。

**建议**：US ticker 允许 `.` / `-` 并做白名单校验；crypto 明确“输入 base asset”或“输入 pair”；`166002` 这类前缀冲突不要靠 prefix 给 quote 能力，或让能力检查走一次源探测。

### CR-20 测试没有覆盖真正的风险点

覆盖率 91.34%，但：

- `server/app.py` 78%、`sync.py` 74%、`tiantian.py` 81%、`eastmoney/quotes.py` 79%。
- 没有 `history` 不同 `limit` 的回归；没有 `limit=0` 的测试。
- 没有“一个有效 + 一个源端缺失”的批量测试；现有批量失败用例用的是 `022430`，在 `_require` 阶段就被拦掉，根本没有进入 `_fetch_group`。
- 没有 `/v1/instruments` 的 `has_more` 断言；`test_listing_is_paginated` 只查了第一页。
- 没有 `estimate` 在指数/持仓/报价失败时的降级测试。
- `tests/test_routing.py:56` 反而把“crypto 没有 quote 路由”固化成了预期，而指南说支持。

**建议**：把上面每个 P0/P1 都变成失败用例；再加并发/取消/缓存增长测试。覆盖率是结果，不是证据。

## 6. P3：低风险与清理项

### CR-21 `as_of` 与 `stale_inputs`

`Estimate.as_of` 的文档是“输入观测时刻”，但 `client/__init__.py:476` 和 `:541` 用的是 `datetime.now()`（计算时刻）。`stale_inputs` 字段没有任何赋值，始终是空元组。要么填充真实输入时间/过期输入，要么删掉字段。

### CR-22 死配置、死指标与依赖

- `src/quotestack/server/config.py:38` 的 `cache_dir` 没有消费者；Docker 里的 `/data` 卷也没有对应实现。
- `src/quotestack/server/metrics.py:23` 的 `REQUEST_COUNTER` 从未 `inc()`，`/metrics` 里永远是 0。
- `_TTL_NAMES` 缺少 `RESOLVE`，环境变量无法覆盖它。
- `pyproject.toml` 把 `pydantic` 放在核心依赖，但只有 `server/schemas.py` 使用；`aiosqlite` 和 `playwright` 两个 extra 在 `src/` 里没有消费者。
- `MarketData` docstring 写“5 req/s, burst 10 / 一次失败后冷却”，实际是 `TokenBucket(4, 1)`、`Cooldown(failure_threshold=2)`。

### CR-23 数据格式与不变量

- `Profile.missing`（`src/quotestack/sources/tiantian.py:182-196`）没有把 `company`（基金管理人）计入，字段缺失时 `partial` 仍为假。
- `tiantian._parse`（`:502`）用 `str(value)` 保存 NAV；JSON 里的 `1.0690` 会变成 `1.069`，丢失固定小数位。建议 `Decimal` 或统一 4 位格式。
- `_to_bar`（`eastmoney/parsing.py:89-127`）不校验 `high >= low`、价格非负；源列顺序变化时只能靠测试发现。
- `Bar` / `NavPoint` 没有 `source`，导致 CR-11 只能在响应层硬编码。

### CR-24 文档与实现的残余漂移

- `guide/02-concepts.md:50` 说 crypto 有报价/K 线（CR-03）。
- `guide/05-estimate.md:131` 说估值不会抛异常（CR-06）。
- `guide/03-quotes.md:22` / `guide/11-troubleshooting.md:21` 说 `status` 会变（CR-09）。
- `guide/06-universe.md:203` 说限流 4 次/秒、2.6 秒扫全量，二者矛盾（CR-07）。
- `identity/rules.py` 的 `cn_exchange` docstring 写 `ValueError`，实际抛 `InvalidArgumentError`。

## 8. 安全与运维

- **CR-12** 是本次唯一直接的安全问题：health 输出代理 userinfo。CLI 最容易被贴进 issue/CI 日志。
- server 默认绑定 `127.0.0.1` 是安全的；指南/Docker 示例用 `0.0.0.0` 时没有认证。作为“行情代理”部署在内网可以接受，但应在文档里明确：不要直接暴露公网；`/v1/instruments` 深分页和 `/metrics` 都可被滥用。
- 日志没有发现 token/密码泄露；`transport` 只记录 URL 和 source，错误 context 里的 `url` 是公开接口地址。
- 没有发现 `eval`、`exec`、`pickle`、`subprocess`、SQL 拼接等高风险用法。
- 异步路径没有阻塞调用（`time.sleep` / 同步文件 IO），只有启动时读 TOML。

## 9. 做得好的地方

- **分层**：`models` 最底层，`identity` 纯规则，`sources` 隔离源差异，`client` 编排，`server` 只做协议转换；`tests/test_architecture.py` 用 AST 守住了 import 方向。
- **错误收口**：`sources/transport.py` 把 httpx 异常统一成 `MarketDataError`，server 用统一信封；这比每个适配器各写一遍强很多。
- **金额类型**：价格/金额/净值全程 `str`，`Decimal` 用于 FX；没有在金额上偷用 `float`。
- **缓存语义**：三态（FRESH/STALE/EXPIRED）+ `max_stale` + 单飞，设计清晰，注释解释了“为什么”。
- **测试习惯**：fixture、坏样本、golden、分层检查、离线测试与 live 探测分离；298 个用例不是摆设。
- **文档工程**：OpenAPI 由代码生成、`sync_docs.py` 生成事实块、`check_docs.py` 检查链接/代码块/状态/计数；这在个人项目里很少见。
- **代码卫生**：`ruff` + `mypy` 全过；没有裸 `except`、没有 `print` 混入库、没有可变默认参数。
